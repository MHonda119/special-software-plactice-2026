## 2. 要件

### 目的

ユーザー名・パスワードによる Django セッション認証を導入し、認証済みユーザーだけが業務 API と保護画面を利用できるようにする。ログイン成功から固定で12時間後に、サーバーと画面の双方で認証を失効させる。

### Issueで決まっていること

- ユーザー登録・管理は Django Admin で行い、アプリ内登録 UI/API は作らない。
- パスワードは Django 標準のハッシュ機構を利用し、API応答にパスワードやハッシュを含めない。
- 認証方式は Django セッションを基本とし、ログイン、ログアウト、現在ユーザー・有効期限取得 API を提供する。
- LLM、セッション、メッセージ、Agent、Datasource、チャンクなど全業務 API で認証を必須にする。Datasourceの所有者列やユーザー単位のデータ分離は行わない。
- 有効期限はログイン時刻を起点にした絶対期限（43,200秒）。API操作で延長しない。期限の強制はサーバー側で行う。
- UIにログイン、ログアウト、未認証時の誘導、期限切れ時の解除を実装する。再読み込み・バックグラウンドからの復帰時もサーバー状態と整合させる。
- 認証エラーを mock API の応答で隠さない。バックエンドの時刻を制御するテストと、ログイン・ログアウト・期限切れのフロント検証を追加する。
- API仕様、Adminでのユーザー登録、環境構築手順を更新する。
- アプリ側の登録、OAuth/SSO、MFA、パスワード再設定、Datasource所有権、既存データの移行・互換性は対象外。

### 受け入れ条件と識別子

- **AC1**: Adminで登録した有効ユーザーはログインでき、不正な資格情報はユーザー名の存在有無を区別できない応答で失敗する。
- **AC2**: 現在ユーザーと認証期限を取得でき、資格情報・ハッシュは公開されない。
- **AC3**: 未認証・ログアウト済み・期限切れの呼び出しは、明示した例外以外のAPI操作で拒否される。
- **AC4**: ログイン後12時間未満は有効、12時間到達以降は無効であり、継続利用しても期限は変わらない。
- **AC5**: 画面上の期限到達、再読み込み、休止からの復帰、手動ログアウトがサーバー状態と一致する。
- **AC6**: 認証エラーはmock APIへ切り替えて隠されない。CSRF拒否、権限不足、認証切れ、通信障害を区別して扱う。
- **AC7**: 時刻制御を含むバックエンドテストと、ログイン・ログアウト・期限切れを扱うフロント検証が追加される。
- **AC8**: API仕様とAdminユーザー登録・環境構築の案内が更新される。

### コードで確認した現状

- `django.contrib.auth`、`django.contrib.sessions`、セッション・認証ミドルウェアは導入済みだが、プロジェクト独自のユーザーモデルはない。Adminは現在のユーザーモデル取得関数でsuperuserを作成している。
- DRFの明示的な既定認証・権限設定はなく、APIルートにはログイン・ログアウト・meがない。`health/` と `csrf/` は既存の独立エンドポイント。
- LLM、ChatSession、Agent、Datasourceのモデルにユーザー外部キーはなく、共有リソースとして扱われている。
- React Routerにログイン画面・認証ガードはない。APIクライアントはHTTPエラーも含む任意の失敗でmockへフォールバックする。
- API仕様書は現行APIが未認証であると記載しているため、認証導入に合わせて共通記述を更新する必要がある。
- Compose/entrypointには固定または既定値のsuperuser資格情報がある。認証導入後にそのまま外部公開するのは危険。

### 仮定・提案（Issueで確定していない）

- **推奨**: カスタムユーザーモデルが必要な追加フィールドはIssueにないため、既存の Django 標準ユーザーモデルを使う。`AUTH_USER_MODEL` の新設は既存DBへの変更・移行負荷が大きく、目的に必要な根拠がない。追加要件が判明した場合は実装前に決定を止めて再計画する。
- ログインAPIは `AllowAny` としつつ明示的なCSRF保護を行う。ログアウト、me、CSRF取得も公開範囲と応答を個別に定義する。`/api/health/` は匿名のまま維持する。
- `/api/` のDRFルート一覧を含むその他のAPIは保護対象とする。API認証はセッションに限定し、Basic認証など意図しない代替認証を許可しない。
- 期限切れはセッション内に保存したログイン時刻をサーバー側で照合し、セッションの単なるCookie期限だけに依存しない。`expires_at` はUTCのISO 8601形式とする。
- 401（未認証・期限切れ）、403（CSRF拒否・権限拒否）の使い分けは実装時にAPI共通仕様として固定する。資格情報不正は一律のステータス・本文とし、ユーザー名の存在を漏らさない。
- Datasourceを含む全リソースは認証後も全ユーザー共有のまま。これは明示された対象範囲だが、機密データを格納する用途には不適切である。

### T1 — 認証契約と標準User採用を確定

- **領域 / 規模**: API・セキュリティ / S
- **作業・成果物**: API利用者向け契約を確定する。推奨案は Django標準User、セッション認証のみ、ログイン成功時に固定期限を記録、`GET /api/auth/me/` が `{user: {id, username}, expires_at}` を返す形式。ログイン・ログアウトの成功応答、資格情報不正の共通エラー、401と403、公開例外を整理する。
- **変更候補**: 実装前の決定事項。コード変更なし。
- **依存**: なし。最初に着手。
- **完了条件**: カスタムUserの必要性、API応答、認証ステータス、匿名例外、期限の時刻基準が記録される。標準Userでよいと確認できれば以降へ進む。
- **検証方法**: Issue AC1–AC6との契約レビュー。実行テストはしない。
- **リスク**: カスタムUser選択は既存DB・マイグレーションへ影響し得る。必要性が未確定なら実装を止め、別途移行判断を行う。

### T2 — Django認証APIとセッション期限を実装

- **領域 / 規模**: バックエンド・API / M
- **作業・成果物**: `POST /api/auth/login/`、`POST /api/auth/logout/`、`GET /api/auth/me/` を追加する。Django `authenticate` / `login` / `logout` と標準Userを使い、ログインのCSRF保護を明示する。不正資格情報はユーザー名の有無にかかわらず同一応答とする。ログイン時刻をセッションに保存し、期限時刻を返す。
- **変更候補**: [backend/core/views.py](../../backend/core/views.py)、[backend/core/urls.py](../../backend/core/urls.py)、[backend/lecture_system/settings.py](../../backend/lecture_system/settings.py)、必要なら新規認証用モジュール（候補）。
- **依存**: T1。
- **完了条件**: API契約どおりにログイン・ログアウト・現在ユーザーが動作し、パスワード/ハッシュが応答に含まれず、ログインCSRFが検査される。
- **検証方法**: 有効/無効ユーザー、匿名me、ログアウト後me、CSRF欠落・有効トークン、応答フィールドのバックエンドテスト。
- **リスク**: DRF APIViewは通常のDjango CSRF保護と挙動が異なる場合がある。匿名ログイン時を含めCSRF検証が実際に有効なことをテストで確認する。

### T3 — 業務API全体に認証・権限を適用

- **領域 / 規模**: バックエンド・セキュリティ / M
- **作業・成果物**: セッション認証と認証必須権限をAPI既定として設定し、認証APIのloginだけを匿名許可する。`health/` と `csrf/` の例外、`/api/` の扱い、OPTIONS/HEADを含むルート挙動を明記する。DatasourceのCRUDとチャンク操作、LLM、session、message、Agentを漏れなく対象にする。
- **変更候補**: [backend/lecture_system/settings.py](../../backend/lecture_system/settings.py)、[backend/core/views.py](../../backend/core/views.py)、[backend/core/urls.py](../../backend/core/urls.py)、[backend/core/tests](../../backend/core/tests/)配下の既存APIテスト。
- **依存**: T1、T2。
- **完了条件**: 匿名・ログアウト済みの全業務API呼び出しは拒否され、ログイン済みセッションは利用でき、指定した匿名例外だけが利用可能。Basic認証等でセッション認証を迂回できない。
- **検証方法**: 各ViewSetとカスタムaction（特にDatasource chunks、Agent execute、session chat/messages）の未認証・認証済みテスト。既存テストの認証前提を更新する。
- **リスク**: 権限適用漏れやDRF標準の401/403差異。エンドポイントを一覧化してテストし、CSRF拒否と未認証拒否を区別する。ログイン後も全ユーザーが同じデータを見られる点はIssueの明示範囲。

### T4 — 12時間の固定期限をサーバーで強制

- **領域 / 規模**: バックエンド・セッション管理 / M
- **作業・成果物**: 43,200秒の期限をログイン時刻基準で保存・照合し、保護APIの全リクエストで期限切れセッションを失効・拒否する。Cookie/セッションバックエンドの期限も整合させ、通常リクエストで期限が延長されない設定にする。境界時刻の比較方法とタイムゾーンを固定する。
- **変更候補**: [backend/lecture_system/settings.py](../../backend/lecture_system/settings.py)、認証/期限検査用モジュール（候補）、[backend/core/tests](../../backend/core/tests/)配下。
- **依存**: T2、T3。
- **完了条件**: 12時間未満は認証可、期限時刻到達後は不可。アクティブなAPIアクセスで期限がずれず、期限切れcookie/sessionの再送でも保護APIに到達できない。
- **検証方法**: 時計を固定・進行させ、期限直前・ちょうど・直後、連続リクエスト、期限切れ後再送、ログアウトを検証する。実時間待ちには依存しない。
- **リスク**: Django標準のセッション有効期限のみでは固定ログイン時刻の強制と再送Cookieの拒否を十分保証しない可能性。認証のたびにサーバー側ログイン時刻を検査し、ブラウザータイマーは補助に限定する。

### T5 — APIクライアントの認証連携とmock誤フォールバック防止

- **領域 / 規模**: フロントエンド・API連携 / M
- **作業・成果物**: 認証API関数と認証状態取得を追加し、401/403/CSRFと通信障害を識別する。認証・権限エラーではmockへ切り替えない。認証APIは常に実バックエンドを使い、mock fallback方針は他のエンドポイントにも明示的に適用する。
- **変更候補**: [frontend/src/services/apiClient.js](../../frontend/src/services/apiClient.js)、`frontend/src/services/`の認証モジュール（候補）、[frontend/src/services/mockApi.js](../../frontend/src/services/mockApi.js)（必要な場合のみ）。
- **依存**: T2、T3。T4のAPI期限応答との統合確認が必要。
- **完了条件**: 認証失敗が成功したmock結果に置き換わらず、401/403と通信障害をUIへ区別可能な形で渡す。CSRF取得・unsafe request時のCookie/ヘッダーが正しく送られる。
- **検証方法**: APIクライアント単体検証またはコンポーネントテストで401、403、CSRF拒否、ネットワーク断、サーバーエラーをそれぞれ確認する。
- **リスク**: 現行の全catch fallbackを単純に残すと認証障害を隠す。fallbackの対象条件を絞り、少なくとも認証・CSRFエラーは必ず伝播させる。

### T6 — ログイン画面、保護ルート、ログアウトを実装

- **領域 / 規模**: フロントエンド/UI / M
- **作業・成果物**: ログイン画面（ユーザー名、パスワード、送信中、失敗表示）、認証状態管理、未認証保護ルート、ユーザー操作によるログアウト導線を追加する。初回ロード/再読み込みで`/auth/me/`を照会する。期限タイマーはサーバー由来の`expires_at`で計算し、タブが復帰した時にも再確認する。
- **変更候補**: [frontend/src/main.jsx](../../frontend/src/main.jsx)、新規ログイン画面（例: `frontend/src/pages/LoginPage.jsx`、候補）、認証状態Provider/ルートガード（例: `frontend/src/`配下、候補）、既存ページのナビゲーション。
- **依存**: T5。T4の期限契約に依存。
- **完了条件**: 未認証ユーザーは保護画面に留まれず、ログイン後は元の遷移先またはメニューへ進み、手動/期限切れ時はログイン画面へ戻る。ブラウザー再読込・復帰時にサーバー状態を再同期する。
- **検証方法**: ログイン成功/失敗、初回未認証、再読み込み、期限切れ、バックグラウンド復帰、ログアウト、送信中表示とアクセシビリティを画面テストで確認する。
- **リスク**: クライアント時刻のずれやタイマー休止。クライアントだけで認証可否を決めず、me/API応答を最終判断とする。パスワードをlocalStorage等に保存しない。

### T7 — テスト・E2Eを認証フローに更新

- **領域 / 規模**: 品質保証 / M
- **作業・成果物**: バックエンドの認証・権限・期限テストを統合し、E2Eへログイン、保護画面、ログアウト、期限切れ遷移を追加する。既存のスタート画面から未認証でメニューへ進む期待とスクリーンショットを新しいフローに更新する。
- **変更候補**: [backend/core/tests](../../backend/core/tests/)、[e2e/tests/start-page.spec.ts](../../e2e/tests/start-page.spec.ts)、E2E設定/fixture（必要な場合の候補）。
- **依存**: T2–T6。各層の実装後に統合。
- **完了条件**: AC1–AC7の自動検証があり、E2E用ユーザー資格情報が安全なテストfixture経由で設定される。実時間で12時間待つテストがない。
- **検証方法**: バックエンドテスト、frontend lint/typecheck/build、Playwright E2Eを計画された検証環境で実行する。これは実装段階の予定であり、本計画作成時には実行しない。
- **リスク**: 既存のE2Eが匿名開始を前提にしている。専用ユーザーをテスト環境で作成し、資格情報をソースコードや公開ログに固定しない。

- **領域 / 規模**: ドキュメント・設定・セキュリティ / M

### 適用順序・互換性

1. T1でユーザーモデルと契約、公開例外、エラーコードを決定する。
2. T2–T4でAPI認証と固定期限を構築する。新フロント導入前にAPIを保護すると、既存フロントはログイン導線がなくアクセス不能になるため、開発環境では両者を同じリリース単位にする。
3. T5–T6のフロント認証フローを統合し、T7でバックエンド/フロント/E2Eを検証する。
4. T8の手順・初期資格情報設定を反映し、Admin利用者とCookie設定を確認してから利用環境へ展開する。
5. 標準Userを採る限り、アプリ独自テーブルのデータ移行・ロールバックは想定しない。既存のDjango標準認証/セッションテーブルのマイグレーション適用状態は事前確認する。もし実装で独自スキーマ変更が必要になった場合は、Issueの既存データ互換性除外だけを根拠に本番DB変更を進めず、バックアップ・復旧または前進修正を含む別の移行計画を作る。

### 監視・復旧

- 展開後は、ログイン成功/失敗、認証拒否、CSRF拒否、期限切れ、ログアウトの件数とHTTPステータスを確認する。資格情報・Cookie・CSRFトークンをログに出さない。
- セッション設定・認証ポリシーの不整合時は、フロントとAPIを同時に戻すか、保護ポリシーを緩和せず前進修正する。認証導入前の未認証APIへ戻すことはセキュリティ上のロールバックとして推奨しない。
- 管理者アクセス不能時に備え、秘密情報を使ったsuperuser作成/パスワード再設定の運用手順を確保する。ユーザー別データ分離を必要とする利用環境では本Issueのまま公開せず、別要件として設計する。

### 並列化と最初の着手候補

- 最初の着手は **T1（契約・標準User確認）**。不確実なUserモデル判断を先に閉じる。
- 次に **T2（ログイン/me/logout API）** を開始し、セッション契約をUIとテストへ渡す。
- T2後、T3とT4は権限の全ルート適用と期限判定の境界を合わせてレビューしながら進める。T5のAPIクライアント整理とT8のドキュメント骨子はAPI契約確定後に並列着手可能。T6はT5および期限応答が固まってから、T7は各層完成後に実施する。

## 6. 未確定事項・判断待ち

1. **Userモデル**: 標準Django Userでよいか。Issueに追加プロフィール要件がないため標準Userを推奨する。カスタムUserを希望する場合は既存DB・初期マイグレーションへの影響を別途評価する。
2. **認証エラーのステータス**: 未認証/期限切れを401、CSRF拒否を403にする案を推奨する。DRF SessionAuthenticationの既定挙動との整合を実装前に決定する。
3. **公開APIの例外**: Issueが列挙するlogin、csrf、healthに限定するか、logoutの未認証時に冪等な成功を返すか、`/api/` のBrowsable APIルートを保護するかをT1で確定する。
4. **Admin初期ユーザー**: Composeの固定 `admin/password` とentrypointの既定資格情報を撤去する方針を推奨する。講義環境でのbootstrap方法（環境変数、手動作成、開発専用設定）を決める。
5. **共有データのリスク**: 認証後も各ユーザーは全LLM/会話/Agent/Datasourceへアクセスできる。ユーザー別分離が必要な実データ環境では、所有権設計を別Issueにする。
6. **Cookie属性・HTTPS**: 開発用HTTPと本番HTTPSのSecure属性、SameSite、CSRF trusted originsをデプロイ環境ごとに確定する。Cookie Secureを有効にする環境ではHTTPS終端・プロキシ設定も合わせて検証する。
