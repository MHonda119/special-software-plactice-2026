## 2. 要件

### 目的

Django 標準の認証・セッション機構を使い、管理者が Django Admin で登録したユーザーだけが認証できるようにする。業務 API には認証を必須とし、認証セッションはログイン時から固定で 12 時間後に失効させる。

### バックエンド受け入れ条件

- **AC-BE-1 — ユーザーとログイン:** Django Admin で登録した有効なユーザーがユーザー名・パスワードでログインできる。認証失敗応答からユーザー名の存在有無を推測できず、パスワード・ハッシュをレスポンスへ含めない。
- **AC-BE-2 — 認証 API:** `POST /api/auth/login/`、`POST /api/auth/logout/`、`GET /api/auth/me/` を提供する。`me` はログインユーザー情報と認証有効期限を返す。
- **AC-BE-3 — 保護範囲:** LLM、会話セッション、メッセージ、Agent、Datasource、チャンク等のすべての業務 API と DRF の `/api/` 一覧ページは、未認証・ログアウト済み・期限切れの状態で拒否される。未認証で利用できる API は `health`、`csrf`、`login` のみとし、`logout` は認証必須とする。
- **AC-BE-4 — 固定期限と CSRF:** ログイン成功時刻から 43,200 秒でサーバー側の認証を失効させ、API 利用で期限を延長しない。ログインを含む更新系 API に CSRF 対策を適用し、セッション Cookie を適切に保護する。
- **AC-BE-5 — バックエンド検証・文書:** 時刻を制御したバックエンドテスト、認証・権限テスト、API 仕様と Django Admin でのユーザー登録・環境設定手順を整備する。
- **AC-BE-6 — リリース告知:** PR の説明に、認証導入後はログイン対応していない既存フロントエンド画面からの API 利用が失敗することを明記する。フロントエンド対応は別作業とする。

### 対象外・制約

- フロントエンドのログイン画面、画面遷移、ログアウト導線、期限到達時の UI 動作、およびフロントエンドテスト。今回の演習範囲外とする。
- ユーザー登録 API/UI、Datasource の所有者設定やユーザー別アクセス制御、OAuth/SSO/MFA、パスワード再設定。
- 既存業務データのユーザーへの割当て、引き継ぎ、互換性維持。
- 初期管理者の固定パスワード変更やブートストラップ方式の変更。固定パスワードは今回は変更せず、講義用ローカル環境向けであり、外部環境では使わない旨を文書に明記する。
- 本計画の作成後にユーザーが確定した決定事項は以下に反映し、コードで確認した現状や提案と区別する。

### コードで確認した現状

- Django の標準 `django.contrib.auth`、Session Middleware、Authentication Middleware は有効だが、`AUTH_USER_MODEL` は指定されておらず、現状は Django 標準ユーザーモデルを利用する構成である。[settings.py](../../backend/lecture_system/settings.py)
- `/api/` 配下に認証 API はなく、業務 ViewSet に認証・権限の明示設定も見当たらない。`/api/health/` と `/api/csrf/` は個別の公開 View として登録されている。[views.py](../../backend/core/views.py) [urls.py](../../backend/core/urls.py)
- API 共通仕様では DRF の標準認証（Session/Basic）と `AllowAny` が適用され、未認証アクセスが可能と記載されている。既存の Agent・Datasource API テストも匿名クライアントを使っている。[README.md](../backend/api/README.md) [test_agent_api.py](../../backend/core/tests/test_agent_api.py) [test_datasource_api.py](../../backend/core/tests/test_datasource_api.py)
- CSRF トークン API と Cookie 関連設定はすでに存在する。セッションの絶対有効期限をログイン時刻から検証する実装は確認できない。[csrf.md](../backend/api/csrf.md) [settings.py](../../backend/lecture_system/settings.py)
- `LLM`、`ChatSession`、`Agent`、`Datasource` 等にユーザー所有者との関連はなく、Admin 以外のユーザーは同一業務データを共有する構造である。[models.py](../../backend/core/models.py)
- 起動時に初期管理者を作る設定があり、Compose とセットアップ文書には固定初期認証情報が設定されている。ユーザー決定により今回は変更せず、講義用ローカル環境向けで外部環境では使わない旨を文書に記載する。[entrypoint.sh](../../backend/entrypoint.sh) [docker-compose.yml](../../docker-compose.yml) [setup.md](../setup.md)
- 既存マイグレーションは業務モデルを作成するもの。ユーザー決定により Django 標準 User を使い、独自 User モデルを作成しないため、ユーザー認証専用の独自モデル追加は計画しない。[migrations/](../../backend/core/migrations/)

### 確定した決定事項

- Django 標準 User を使い、独自 User モデルは作らない。
- 12 時間の固定期限は Django Admin を含むすべての認証セッションに適用する。
- 未認証で使える API は `health`、`csrf`、`login` のみ。`logout` と DRF の `/api/` 一覧ページを含むその他すべての API は認証必須とする。
- API 認証は Django セッション認証のみとし、Basic 認証は無効にする。
- 初期管理者の固定パスワードは変更しない。講義用ローカル環境向けであり、外部環境では使わない旨をドキュメントに明記する。初期管理者設定のコード変更は対象外。
- ユーザーごとの業務データ分離は行わない。
- フロントエンド連携は行わない。認証導入後に既存画面からの API 利用が失敗することを計画と実装 PR に明記する。

## 4. タスク分解

### T-01 — 確定済み認証ポリシーを実装契約へ落とし込む

- **領域・目的:** バックエンド／API。ユーザーが確定した認証方針をルート・permission・認証方式・期限の実装契約にする。
- **作業・成果物:** Django 標準 User、セッション認証のみ、Basic 無効、Admin を含む全認証セッションに固定期限、匿名許可は `health`・`csrf`・`login` のみ（logout と DRF API 一覧は認証必須）という一覧を作る。ログイン・未認証・期限切れ時の HTTP ステータスと応答形、Admin セッションを同じ期限検査へ含める方法を整理する。
- **候補パス:** [settings.py](../../backend/lecture_system/settings.py)、[urls.py](../../backend/core/urls.py)、[README.md](../backend/api/README.md)。
- **依存:** なし。
- **完了条件:** 全 API ルートと Django Admin の認証セッションが確定済みの保護・期限方針に分類され、実装担当者に認証方式や公開例外の判断待ちが残らない。
- **検証方法:** 確定事項と URL 一覧・Admin の認証経路を照合するレビュー。テスト実行はしない。
- **リスク:** DRF のルート一覧や Admin の標準認証経路が対象から漏れると、意図しない匿名アクセスや期限迂回が生じる。
- **規模:** S。

### T-02 — Django セッション認証 API を実装する

- **領域・目的:** バックエンド／API。ログイン・ログアウト・現在ユーザー情報を提供する。
- **作業・成果物:** `POST /api/auth/login/` で標準認証バックエンドを使ってログインし、失敗時はユーザー名有無にかかわらず同じエラー形にする。`POST /api/auth/logout/` は認証セッションをサーバー側で無効化する。`GET /api/auth/me/` は決定済みの最小ユーザー情報と有効期限を返し、パスワード・ハッシュ等を含めない。ログイン自体にも CSRF 検証を適用する。
- **候補パス:** [views.py](../../backend/core/views.py)、[urls.py](../../backend/core/urls.py)、[serializers.py](../../backend/core/serializers.py)、必要なら新規 `backend/core/authentication.py` または `backend/core/auth_views.py`。
- **依存:** T-01。
- **完了条件:** 3 エンドポイントが確定契約どおり応答し、Django 標準のハッシュ化パスワード照合と Session Cookie を用いる。logout 後の Cookie/サーバーセッションは無効で、me に秘密情報を出力しない。
- **検証方法:** 有効・無効ユーザーのログイン、同一形の失敗応答、me のフィールド allowlist、ログアウト後のアクセスを API テストで確認する。
- **リスク:** ログインの CSRF 保護が DRF の匿名アクセス挙動だけに依存すると保護されない可能性がある。CSRF 強制を明示的に検証する。
- **規模:** M。

### T-03 — 業務 API 認証と絶対有効期限を強制する

- **領域・目的:** バックエンド／認可・セッション。すべての保護対象操作をサーバー側で制限する。
- **作業・成果物:** DRF の既定 Permission を認証必須にし、`health`・`csrf`・`login` のみを公開する。logout、DRF の `/api/` 一覧ページ、すべての業務 API は認証必須とする。API 認証は SessionAuthentication のみにし、BasicAuthentication を無効にする。ログイン時刻から算出した絶対期限をサーバー側に保持・検査し、`now >= login_time + 43,200 秒` で Django Admin を含むすべての認証セッションを失効させる。リクエストでログイン時刻や期限を更新しない。ログアウト済み・期限切れセッションの再利用を拒否する。Session Cookie と CSRF Cookie の Secure/HttpOnly 等は開発・HTTPS 環境に合う設定にする。
- **候補パス:** [settings.py](../../backend/lecture_system/settings.py)、[views.py](../../backend/core/views.py)、[urls.py](../../backend/core/urls.py)、必要なら新規期限検査 middleware/authentication helper。既存の [csrf.md](../backend/api/csrf.md) に記載された設定も整合させる。
- **依存:** T-01、T-02。
- **完了条件:** LLM、sessions/messages/chat、Agents/execute、Datasources/chunks、DRF の API 一覧が匿名・logout 済み・期限切れ状態を拒否し、`health`・`csrf`・`login` のみ匿名利用できる。Basic 認証が使えず、Admin を含む全認証セッションが閾値前は有効、到達時点から無効であり、API 操作による延長がない。すべての unsafe method に CSRF 検証が適用される。
- **検証方法:** 代表ルートと API 一覧の匿名拒否、3つの公開例外、logout の認証必須、Basic 認証拒否、Admin と API のログイン後許可、CSRF 不正時の拒否、時刻制御による 43,199 秒時点と 43,200 秒時点、期限後の再送、長時間の継続利用でも期限が不変であることをテストする。
- **リスク:** Django セッションの Cookie/保存期限だけに依存すると、セッション更新による期限延長を防げない場合がある。Admin と API の両方の認証経路を同じ絶対期限に結びつける必要がある。
- **規模:** M。

### T-04 — 認証 API と期限の自動テストを追加する

- **領域・目的:** バックエンド／テスト。API の機能・境界条件を固定する。
- **作業・成果物:** 認証 API 用テストを追加し、ユーザー作成は Django の標準 User/`create_user` を通じて行う。時刻は mock/patch 等で制御し、実時間待ちを使わない。
- **候補パス:** 新規 `backend/core/tests/test_auth_api.py`、必要に応じて新規 `backend/core/tests/test_auth_permissions.py`。
- **依存:** T-02、T-03。
- **完了条件:** Admin 作成ユーザーの認証、誤パスワードと不明 username の応答同一性、me の情報漏えい防止、CSRF、logout、期限境界・非延長・期限後拒否が回帰テスト化される。
- **検証方法:** 新規認証テストを Django の既存テスト環境で実行。Cookie 検証には必要に応じて CSRF チェック有効のクライアントを使用する。
- **リスク:** `force_login` だけで確認すると実際のログイン CSRF・認証経路を検証できないため、実ログインを通すテストを含める。
- **規模:** M。

### T-05 — 既存業務 API テストを認証前提へ移行する

- **候補パス:** [test_agent_api.py](../../backend/core/tests/test_agent_api.py)、[test_datasource_api.py](../../backend/core/tests/test_datasource_api.py)、既存 API テストモジュール。セッション/LLM API の既存テストがなければ必要なテストファイルを追加する。
- **依存:** T-03。

- **検証方法:** 変更対象の API テストと、業務 API ルートごとの未認証アクセス行列を実行・レビューする。
- **リスク:** 成功テストだけを認証化し、保護漏れを検査しないと一部の ViewSet/追加アクションが匿名公開のまま残る。
- **規模:** M。

### 実行順・並列化

1. T-01 で確定済みのユーザーモデル、公開例外、認証方式、全セッションの期限を実装契約にする。
2. T-02 の認証 API と T-03 の保護・期限を順に実装する。設定・View の共有箇所があるため、同時変更は担当間で調整する。
3. T-04/T-05 のテストは T-03 の契約固定後に分担可能。初期管理者ブートストラップの変更タスクは設けない。
4. T-06 文書を実装契約に合わせ、T-07 でバックエンド全体を検証する。

**最初に着手する候補:** T-01（確定済み認証ポリシーの実装契約化）、続いて T-02（標準 User 前提の認証 API）。

### 展開・監視・復旧

- Django 標準 User を利用し、独自 User モデル・ユーザー所有者列は追加しない。既存データのユーザー別移行は行わない。
- 初期管理者の固定パスワードは今回は変更しない。講義用ローカル環境向けであり、外部環境では使わないとセットアップ文書に明記する。初期管理者設定コードや Compose 設定は本計画の変更対象外とする。
- ログイン成功・失敗、期限切れ拒否、CSRF 拒否の監視は秘密情報を記録せず件数・ステータス等で確認する。パスワード、Cookie、セッション識別子、CSRF トークンはログへ出さない。
- 本変更のロールバックで API を再び匿名許可すると保護が失われるため、単純な権限解除を復旧策にしない。問題時は影響を受ける認証 API/期限処理を前進修正し、必要なら保護された状態を維持したまま段階リリースを止める。
- バックエンド認証が有効になると、現行フロントエンド画面からの API 利用は失敗する。フロントエンド対応は本計画の対象外。後続実装の PR にこの影響を明記し、フロントエンド対応を含む統合リリースの時期は別途調整する。

## 6. 未確定事項・リスク

### 決定済み事項

1. **ユーザーモデル:** Django 標準 User を使い、独自 User モデルは作らない。
2. **固定期限:** 12 時間の絶対期限を Django Admin を含むすべての認証セッションに適用する。
3. **公開範囲:** 未認証で利用できる API は `health`、`csrf`、`login` のみ。`logout` と DRF の API 一覧を含むその他すべては認証必須。
4. **認証方式:** Session 認証のみとし、Basic 認証は無効にする。
5. **初期管理者:** 固定パスワードは変更しない。講義用ローカル環境向けであり、外部環境では使わないと文書に注意書きを残す。ブートストラップの実装変更は対象外。
6. **データ分離:** ユーザーごとのデータ分離は行わず、認証済みユーザー間で共有する。
7. **フロントエンド:** 今回は連携しない。認証導入後は既存画面からの API 利用が失敗することを計画と後続 PR に記載する。

### 残存リスク

- 上記の認証ポリシーに関する判断待ちはない。実装時は確定事項をそのまま適用する。
- Django 標準のセッション期限設定だけでは、操作時に期限が延長される可能性がある。サーバー側でログイン時刻を起点とする絶対期限を検査し、Admin と API の双方で境界時刻をテストする。
- 固定初期管理者パスワードのまま外部環境で稼働させることは認めない。ドキュメントに注意書きを残すが、実環境での誤用を構成で防ぐ変更は今回行わないため、利用環境の制約を運用時に守る必要がある。
- バックエンドのみの認証導入により、既存画面からの API 利用は失敗する。後続 PR では影響を明記し、フロントエンドを含む統合時期を別途調整する。
